# RNL public packages

Optional packages for [RNL](https://github.com/rich-netlist/rnl). The standard series, including `rnl-zh`, stays in RNL and is built into its viewers.

| Package | Version | Kind |
| --- | --- | --- |
| analog-canvas-extensions | 0.1, 0.2, 0.3, 0.4 | extension |
| eda-symbol | 0.1 | extension |
| eda-style | 0.1 | extension |
| pdk-sky130 | 0.1 | pdk |

The package files, examples and package READMEs retain their original bytes. Their history was imported from RNL main (the exact source revision is in `rnl-revision.txt`) using git-filter-repo, selecting the four former library directories and `scripts/pdk/`, and renaming the library directories to `packages/NAME/VERSION/`.

## Use

The catalog is published at <https://rich-netlist.github.io/rnl-packages/catalog.json>. Versioned files remain at `https://rich-netlist.github.io/rnl-packages/packages/NAME/VERSION/NAME.rnl` forever.

In the web viewer choose **File → Include Public Package…**, then name the package in the netlist:

```spice
* @RNL(type="header") { @VERSION("0.3"); @USE-PACKAGE(name="eda-symbol", version="0.1") }
```

For the CLI, download the version from its catalog URL, verify its SHA-256 against the catalog, and run `rnl check circuit.sp --path /downloaded/packages/eda-symbol/0.1`. The same directory works with `rnl render`. Include dependencies as separate package directories when needed.

## Catalog format (schemaVersion 1)

`catalog.json` is generated by `python scripts/catalog.py`; do not edit it by hand. It contains `schemaVersion: 1` and a `packages` array, one record per name/version:

- `name`, `version`: exactly the package header. RNL 0.3 §16.2 requires `major.minor`, with each 0.x a separate major. No patch numbers or preview suffixes.
- `kind`: `extension` or `pdk`; `summary`: the English summary from `metadata.json`, `{"en": "…"}`. The four imported 0.1 records also keep the Chinese they were published with. Translations are outside the records, in `summaries/` (below).
- `url`, `sha256`: the immutable primary file URL and lowercase hexadecimal SHA-256 of its raw bytes.
- `path`: a globally unique path in the viewer's file pool. Only the four imported 0.1 records retain their published library-relative paths for compatibility; every new version and new package name uses `NAME/VERSION/NAME.rnl`. The generator rejects duplicate paths. `description`: the original first paragraph shown in the package picker.
- `source`: the GitHub source URL. `assets`: every file in the version directory, each with a relative `path`, immutable `url` and raw-byte `sha256`, including README and examples.

Consumers must reject an unsupported schema or hash mismatch. Resolve relative URLs against the catalog URL (offline fixtures use relative URLs). Select the latest version numerically by major and minor, or select an exact locked name/version and check its locked SHA-256. Published records and all their assets are append-only: CI compares the generated catalog with the target branch / previous main commit, rejects removed or changed records, and checks that the committed catalog is generated from the files. Keep published metadata unchanged too.

## Translations of the summaries

English is RNL's only core language ([decision 0015](https://github.com/rich-netlist/rnl/blob/main/docs/decisions/0015-english-is-the-only-core-language.md)): a record's summary is in English, and its translations are in `summaries/LANG.json`, such as [`summaries/zh.json`](summaries/zh.json), published at `https://rich-netlist.github.io/rnl-packages/summaries/LANG.json`. Each file is an object keyed by the English of a record's summary, with its runs of white space as one space; a value is the translation, or `null` where there is none yet. The files are not part of any record and are not hashed, so a translation can be added or corrected at any time, in a pull request of its own. `python scripts/catalog.py --check` rejects a key that is not the English summary of a record. A consumer shows a record's own translation first, then the one in the file, then the English.

## Publish a version

1. Create a branch and copy a package to a **new** `packages/NAME/major.minor/` directory. Update that copy's `@PACKAGE` version. Never edit or remove a published directory or its metadata.
2. For a new name add its kind and its English summary, `{"en": "…"}`, to `metadata.json`; no `legacyPath` is needed. Its translations go into `summaries/`, now or later. For an existing name retain its metadata; a version that adds something may get a summary of its own, `"versions": {"major.minor": {"summary": {"en": "…"}}}`, which only its record uses. New records always get version-qualified paths; the four imported 0.1 records remain byte-for-byte unchanged.
3. Run `python scripts/catalog.py`, then `python scripts/catalog.py --check --base origin/main`. Review the generated URLs and hashes.
4. Open an English pull request. CI checks all package headers and immutable records, reads every version without errors and renders every symbol with the **exact RNL commit in `rnl-revision.txt`**; it also runs `sky130.py --check`, including the PDK examples and stub models.
5. After review and merge, the main workflow publishes the validated catalog and all versions to this repository's GitHub Pages. Verify the deployed catalog and hashes. There are no npm releases or Git tags in this process.

To upgrade the checker, change only `rnl-revision.txt` to a reviewed full RNL commit, then run the same CI. Its checkout, `Cargo.lock` (`cargo build --locked`), and the same WebAssembly renderer used by RNL's viewer make the validation reproducible. Pages settings use **GitHub Actions** as the deployment source. GitHub Pages serves these static assets with cross-origin access for the RNL site and embedded viewers.
